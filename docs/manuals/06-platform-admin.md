# 플랫폼 관리자 (MonoFlip 기술 관리자, PLATFORM_ADMIN) 매뉴얼

> **대상**: AI Pajak 의 **플랫폼·인프라·사용자·청구 관리**를 담당하는 `PLATFORM_ADMIN` 계정 보유자 (MonoFlip 기술팀)
>
> **매우 중요한 제약**: 플랫폼 관리자는 **고객의 세무 데이터에 접근할 수 없습니다.** 이것은 협상 불가능한 보안 규칙입니다 (Hard Rule #1 + #6 — P6.1 신설).
>
> **PLATFORM_MASTER 와의 차이**: MonoFlip 사업 운영 최고권한 (요금·상품·통계·계약) 은 **[PLATFORM_MASTER](./08-platform-master.md)** 별도 role 입니다. PLATFORM_ADMIN 은 **기술관리자** (개발·서버·로그·장애·결제웹훅) 성격.
>
> - 볼 수 있는 것: 사용자 계정, 역할, 조직, 구독, 결제 상태, 시스템 상태, 감사 로그, AI 사용량, 세율 설정
> - 볼 수 없는 것: 고객 NPWP 상세 데이터, 신고서 내용, 급여 정보, 재무 데이터, Faktur Pajak 내용

## 1. 플랫폼 관리자가 하는 일

### 1.1. 책임 영역
- **사용자·권한 관리** — 신규 가입 승인, 역할 부여, 비활성화
- **컨설턴트·사무소 관리** — 외부 tax_partner 검증·승인
- **시스템 상태 감시** — 에러율, 응답 시간, DB·외부 API 상태
- **크론 작업 운영** — 자동화 스크립트 설정·재실행
- **청구 모니터링** — 구독·결제 현황 조회 (수정 권한 없음)
- **AI 사용량 추적** — OpenAI·Anthropic 토큰 비용
- **감사 로그 감독** — 모든 사용자 조치 기록 조회
- **세율·규칙 관리** — PTKP, PPh 브래킷, 자동 승인 규칙 업데이트

### 1.2. 직접 하지 않는 일 (다른 역할의 몫)
| 일 | 담당 |
|---|---|
| 고객 세무 데이터 입력·열람 | CUSTOMER / CONSULTANT / 외부 컨설턴트 |
| 신고 제출 큐 처리 | TAX_OPERATOR, SUPERVISOR |
| 플랫폼 수익·맞춤 가격 | TAX_OPERATOR_MASTER |
| 실제 DJP 제출 | TAX_ADVISOR, 운영팀 |

## 2. 계정과 로그인

### 2.1. 계정 생성 경로
- 플랫폼 관리자 계정은 **기존 PLATFORM_ADMIN 또는 시스템 최초 설치 스크립트**로만 생성됩니다.
- 최초 설치: `scripts/seed-test-users.ts` 또는 환경별 초기 스크립트에서 부트스트랩
- 이후 추가: 기존 관리자가 `/admin/users` 에서 수동으로 역할 부여

### 2.2. 보안 정책 (강제)
- **2FA 필수** — 첫 로그인 시 TOTP 등록 강제. 미등록 시 모든 `/admin/*` 접근 차단
- **세션 만료** — 비활동 30분 후 자동 로그아웃
- **IP 제한** (옵션) — 특정 IP 대역에서만 로그인 허용 가능
- **로그인 알림** — 새 기기·브라우저 로그인 시 이메일 발송

## 3. 대시보드와 사이드바

### 3.1. 첫 화면
로그인하면 **시스템 상태 요약**, **오늘의 에러 수**, **미결 가입 신청**, **외부 사무소 승인 대기** 등이 표시됩니다.

### 3.2. 사이드바 메뉴

**관리 섹션 (PLATFORM_ADMIN 전용)**

- **모니터링** (`/admin/monitoring`) — 에러율, 응답 시간, Circuit Breaker 상태, 메모리·CPU, Web Vitals
- **크론 관리** (`/admin/cron`) — 스케줄된 자동화 작업 목록, 수동 실행
- **사용자 관리** (`/admin/users`) — 모든 사용자 조회·역할 변경·비활성화
- **청구 관리** (`/admin/billing`) — 구독 현황 조회 (열람 전용)
- **컨설턴트·사무소** (`/admin/consultants`) — 외부 tax_partner 승인·관리
- **AI 사용량** (`/admin/ai-usage`) — OpenAI·Anthropic 토큰 소비량과 비용
- **감사 로그** (`/admin/audit-logs`) — 전체 audit_log 검색
- **세율 설정** (`/admin/tax-rates`) — PTKP, PPh 브래킷, PPN율
- **재정의 규칙** (`/admin/override-rules`) — 특수 케이스 규칙
- **규칙 테스트** (`/admin/rule-test`) — 승인 규칙 시뮬레이터

**계정**
- **청구** — 본인 결제 관련만 (관리자도 구독 대상이 아니면 빈 화면)
- **설정** — 프로필, 2FA, 알림
- **도움말**

## 4. 핵심 플로우

### 4.1. 플로우 A — 신규 사용자 가입 감독

**시나리오**: 누군가 `/register`에서 가입 → 역할이 기본값으로 부여됨 → 관리자가 확인

1. **사용자 관리** (`/admin/users`) → 상단 필터 "가입 30일 이내"
2. 목록에서 신규 사용자 이메일과 역할 확인
3. 의심스러운 가입 (이메일 패턴, 동일 IP 대량 가입 등) 감지 시 **비활성화** 버튼
4. 정상 가입이면 그대로 유지
5. 역할 승격 필요 시 (예: 외부 컨설턴트 신청자를 CONSULTANT로 인정) **역할 편집** → 저장 → 자동으로 감사 로그에 기록

### 4.2. 플로우 B — 외부 세무사무소 승인

**시나리오**: 외부 세무사무소가 회원가입 → `tax_partner` 레코드 생성됨 → 검증 필요

1. **컨설턴트·사무소** (`/admin/consultants`) → 필터 "미승인 외부 사무소"
2. 사무소 상세 확인 — 사무소명, NPWP Badan, 대표자, 첨부 서류
3. **사업자등록증 원본 확인** — 첨부된 PDF 검증
4. 이상 없으면 **승인(is_verified = true)** → 사무소가 구독 결제를 진행할 수 있게 됨
5. 이상 있으면 **반려** 사유 입력 → 사무소에 이메일 발송

### 4.3. 플로우 C — 시스템 장애 대응

**시나리오**: 대시보드에 "DJP API 응답 없음" 경고가 올라옴

1. **모니터링** → Circuit Breaker 상태 확인
2. DJP 관련 breaker가 **OPEN** 상태면 외부 장애임 → 공지 배너 게시 검토
3. **에러 로그** 탭 → 최근 10분간 500 에러 목록 → Sentry 링크로 이동하여 스택 트레이스 확인
4. 인프라 이슈(메모리, DB 커넥션 풀)면 즉시 조치 요청 (Vercel, Supabase 대시보드)
5. 장애 해제 후 breaker가 자동으로 **HALF_OPEN → CLOSED** 로 복구되는지 확인
6. 감사 로그에 조치 내용 메모 (시스템 자동 기록 외 추가 코멘트)

### 4.4. 플로우 D — 크론 작업 재실행

**시나리오**: 매일 오전 6시 세금 캘린더 알림 크론이 실패

1. **크론 관리** → 실패 건 목록
2. 해당 크론 상세 → 실패 로그 확인 (예: SMTP 타임아웃)
3. 원인 조치 후 **수동 실행** 버튼 → 재시도
4. 성공 시 완료, 실패 시 오류 로그를 개발팀에 전달

### 4.5. 플로우 E — AI 사용량 검토

**시나리오**: 월초에 OpenAI/Anthropic 비용이 예산 초과 우려

1. **AI 사용량** (`/admin/ai-usage`) → 이번 달 합계
2. 기능별 세분화:
   - OCR (문서·인보이스 캡처)
   - 세무 자동 답변 (챗봇)
   - 이상 탐지 분석
3. 특정 고객이 과도하게 사용하는 경우 식별 → 사용 제한 고려
4. 비용 최적화 아이디어를 JTC 대표에게 보고

### 4.6. 플로우 F — 감사 로그 검색

**시나리오**: "지난주에 고객 X의 데이터를 누가 열람했는가?" 내부 감사 문의

1. **감사 로그** (`/admin/audit-logs`) → 필터
   - **customer_id** = X
   - 기간: 지난 7일
   - activity_type: `READ_*` 류
2. 결과 목록에서 접근자(actor_user_id), 시점, IP 확인
3. 이상한 접근 패턴(심야 대량 조회 등) 있으면 해당 사용자 계정 비활성화 검토
4. 감사 보고서 PDF로 내보내기

## 5. 세율과 규칙 관리

### 5.1. 세율 설정 (`/admin/tax-rates`)
- **PTKP** — 연 1회 이상 업데이트 (PMK 개정 시)
- **PPh21 브래킷** — 누진세율 구간
- **PPN율** — 기본 11%, 특수 품목별 다름
- **UMKM Final** — 현재 0.5%

수정 시 변경 이력이 자동 기록되며, **효력 발생일**을 미래 날짜로 설정하면 해당 날짜부터 자동 적용됩니다.

### 5.2. 재정의 규칙 (`/admin/override-rules`)
특정 케이스에서 기본 규칙을 덮어쓰는 예외 규정. 예: 특정 업종은 UMKM Final 대신 일반과세 강제.

### 5.3. 규칙 테스트 (`/admin/rule-test`)
새 규칙을 적용하기 전에 샘플 데이터로 시뮬레이션. 실제 DB에 영향 없이 "이 규칙을 적용하면 고객 A의 PPh21이 얼마가 될까"를 미리 계산합니다.

## 6. 청구 모니터링 (열람 전용)

### 6.1. 볼 수 있는 것
- 전체 활성 구독 수 (법인 플랜·외부 사무소 Tier 합계)
- 월별 수익 추이 (그래프)
- 결제 실패 건 목록
- 맞춤 가격 견적 현황 (DRAFT/SENT/ACCEPTED 분포)

### 6.2. 할 수 없는 것
- 구독 취소·환불 (Master 또는 JTC 대표 권한)
- 맞춤 가격 발행 (Master 전용)
- 할인 적용 (내부 정책으로 제한)

열람 권한만 있는 이유는 **Hard Rule #4**(Billing Collector ≠ Service Provider) 때문입니다. 청구 수정은 SYSTEM/MASTER 역할이 담당합니다.

## 7. 보안과 감사

### 7.1. 감사 로그 정책
- **모든 관리자 조치**는 `audit_log` 에 저장됩니다
- `actor_user_id`, `activity_type`, `activity_details`, IP, User-Agent, 타임스탬프
- 로그는 **삭제 불가**, 최소 7년 보존

### 7.2. Row Level Security
- PLATFORM_ADMIN 계정은 **`customer`, `tax_filing`, `monthly_payslip`** 등 고객 데이터 테이블에 **RLS 정책으로 차단**됩니다
- `blockPlatformAdmin` 미들웨어도 API 레벨에서 동일한 차단 수행
- 이 제약은 Hard Rule #1

### 7.3. 2FA와 세션
- 2FA 미등록 계정은 `/admin/*` 접근 시 설정 페이지로 강제 리다이렉트
- 세션 만료 후 재로그인 시 2FA 다시 요구

## 8. 모니터링 대시보드 상세

### 8.1. `/admin/monitoring` 에서 확인할 지표
- **에러율**: 지난 1시간/1일 5xx 에러 개수
- **응답 시간**: API 경로별 p50/p95/p99
- **Circuit Breaker**: DJP, Midtrans, OpenAI, Anthropic, SMTP 각각의 상태
- **메모리 사용량**: Vercel Functions 기준
- **Web Vitals**: LCP, FID, CLS, FCP, TTFB, INP
- **활성 사용자**: 최근 5분 내 활동한 세션 수

### 8.2. Sentry 연동
- 에러 발생 시 자동으로 Sentry에 캡처
- `/admin/monitoring` 의 각 에러 항목에서 **Sentry 링크** 클릭 시 스택 트레이스·브라우저 정보 확인

## 9. 자주 묻는 질문

**Q. 고객이 "제 신고서 좀 봐 달라"고 요청합니다.**
A. PLATFORM_ADMIN은 신고 데이터에 접근할 수 없습니다. 담당 JTC 세무사에게 연결해 주세요.

**Q. 외부 사무소 가입 승인을 했는데 아직 로그인이 안 됩니다.**
A. 사무소가 **구독 결제**를 완료해야 기능이 활성화됩니다. `/admin/consultants` → 해당 사무소 → 구독 상태 확인.

**Q. Circuit Breaker가 자주 OPEN 됩니다.**
A. 특정 외부 API의 신뢰성 문제입니다. 빈도 높은 API가 DJP라면 DJP 장애, Midtrans면 결제 장애. 장기 지속 시 내부 circuit breaker 파라미터 조정 (실패 임계값, 재시도 윈도우) 고려.

**Q. 크론 작업이 "이미 실행 중"이라며 재시작이 안 됩니다.**
A. 이전 작업이 락을 걸고 종료되지 않았을 수 있습니다. 락 테이블에서 락 해제 후 재시작. 자세한 건 개발팀에 문의.

**Q. AI 사용량이 한 고객 때문에 급증합니다.**
A. 해당 고객의 OCR/챗봇 호출 수를 확인. 남용이면 rate limit 적용 검토. 남용이 아니라 정상 사용이면 비용 위탁 합의 필요.

**Q. 감사 로그 검색이 느립니다.**
A. `audit_log` 테이블 크기가 커지면 인덱스 추가 또는 파티셔닝 필요. 개발팀에 성능 개선 요청.

**Q. 플랫폼 관리자 자신의 비밀번호를 잊었습니다.**
A. 다른 관리자에게 리셋 요청. 단독 관리자면 Supabase 대시보드에서 직접 auth 테이블 조작 (매우 위험, 최후 수단).
